## Progressive Web App (PWA)

Rental Platform OS ships Tier 1 PWA support for the two operational portals. Instead of one shared web app manifest, each portal is installable as its own app with its own name, colors, icon set, URL scope, and start URL.

### PWA Library

- **Library**: `serwist` + `@serwist/next` (via `withSerwistInit` in `next.config.ts`)
- **Why**: Modern and actively maintained `next-pwa` fork with Next.js 16 compatibility
- **Build artifact**: Service worker source lives at `src/app/sw.ts` and compiles to `public/sw.js` during build
- **Next.js integration config**: `withSerwistInit({ additionalPrecacheEntries: [{ url: "/~offline", revision }], swSrc: "src/app/sw.ts", swDest: "public/sw.js" })`
- **Offline fallback precache**: `next.config.ts` explicitly precaches `/~offline` using a revision derived from `git rev-parse HEAD` (fallback: `crypto.randomUUID()`)

### Offline Behavior (Tier 1)

Included in V1 Tier 1:

- Install prompt support and home-screen launch for guard/admin portals
- Static asset precache through Serwist-generated service worker
- Offline fallback route at `src/app/~offline/page.tsx`
- Service worker runtime config in `src/app/sw.ts`: `runtimeCaching: defaultCache`, `navigationPreload: true`, `skipWaiting: true`, `clientsClaim: true`
- Document fallback matcher in `src/app/sw.ts` routes navigation requests to `/~offline`
- `src/proxy.ts` includes `/~offline` in `unauthenticatedPaths` so fallback is accessible without auth

Explicitly NOT included in Tier 1 (deferred to later phases):

- Offline mutation queue / background sync
- Push notifications
- Offline-first Convex data replication

Service worker scope is static-asset/offline-fallback focused. Convex real-time traffic is unaffected — WebSocket connections are not intercepted.

### PWA Build + Tooling Constraints

- `npm run build` uses `next build --webpack` (Serwist requires webpack for service worker compilation)
- `npm run preview` runs `npm run build && next start -p 3000` for production-like local validation
- `npm run dev` uses Turbopack; service worker assets are not compiled in dev mode
- `.gitignore` excludes generated worker artifacts: `public/sw.js`, `public/sw.js.map`, `public/swe-worker-*.js`, `public/swe-worker-*.js.map`
- `tsconfig.json` excludes `src/app/sw.ts` so app type-checking does not treat service-worker globals as standard app runtime globals

## Authentication Architecture

### WorkOS AuthKit + Convex Integration

WorkOS is the **default auth provider for Convex** (since Sep 2025). The integration uses TWO packages:

1. `@convex-dev/workos-authkit` — Convex component that auto-syncs WorkOS users, handles webhooks, provides `authKit.getAuthUser(ctx)`
2. `@workos-inc/authkit-nextjs` — Next.js SDK for middleware, session management, and the `saveSession()` / `getSignInUrl()` helpers

**Setup**: Register the component in `convex/convex.config.ts`. Convex validates WorkOS-issued JWTs via two custom JWT providers (SSO + User Management). The component can auto-generate these via `authKit.getAuthConfigProviders()`, or configure manually.

**Guard Login Flow** (Custom UI — NOT AuthKit hosted):

- Guard enters **phone number + password** on our custom login page (`/guard/login`)
- Next.js Server Action converts phone to synthetic email (`{phone}@guards.local`)
- Server Action calls `getWorkOS().userManagement.authenticateWithPassword({ email, password })`
- On success: `saveSession()` stores the session cookie (access token + refresh token)
- `ConvexProviderWithAuth` + `useAuthFromAuthKit()` hook bridges the token to Convex
- If `must_change_password` is true: middleware redirects to `/guard/change-password`
- **Why Server Action, not Convex Action**: Convex Actions can't set browser cookies. The auth session must be stored as an httpOnly cookie by the Next.js server.

**Admin Login Flow** (AuthKit Hosted UI):

- Admin clicks "Sign in with Google" on `/admin/login`
- `getSignInUrl()` redirects to WorkOS hosted AuthKit page (shows Google SSO button)
- After Google SSO: WorkOS redirects to `/callback` route
- Callback handler exchanges code for tokens, `saveSession()` stores session cookie
- On first SSO login: `@convex-dev/workos-authkit` webhook creates the WorkOS user record. The `user.created` event handler in `convex/auth.ts` auto-creates the Convex `users` record (`user_type: ADMIN`, `status: ACTIVE`).

**User Sync**: The `@convex-dev/workos-authkit` component automatically syncs WorkOS users to Convex via webhooks. Event handlers in `convex/auth.ts` map WorkOS events to our custom `users` table:

- `user.created` → Create `users` record (detect guard vs admin by email pattern)
- `user.updated` → Update `users` record
- `user.deleted` → Soft-delete `users` record

**Session Management**:

- WorkOS handles sessions and token refresh via `@workos-inc/authkit-nextjs` middleware
- **Session duration: 30 days** — guards almost never re-login
- Convex receives access tokens via `ConvexProviderWithAuth` wrapper
- `authKit.getAuthUser(ctx)` in Convex functions returns the WorkOS user object
- Our auth helpers then look up the custom `users` table by WorkOS user ID

### Login Pages

**Guard Login** (`/guard/login`):

- Custom phone number + password form (NOT AuthKit hosted UI)
- Phone entered as digits → Server Action converts to synthetic email (`{phone}@guards.local`)
- Server Action calls `getWorkOS().userManagement.authenticateWithPassword()` directly
- On success: `saveSession()` sets httpOnly cookie → redirect to `/guard/dashboard`
- If `must_change_password` is true: middleware redirects to `/guard/change-password` before any other page

**Admin Login** (`/admin/login`):

- "Sign in with Google" button → `getSignInUrl()` redirects to WorkOS hosted AuthKit page
- WorkOS handles Google SSO → redirects to `/callback`
- On first SSO login: auto-creates Convex user record via webhook event handler
- On success: redirect to `/admin/dashboard`

**Auth Callback** (`/callback`):

- Handles the OAuth callback from WorkOS AuthKit
- Uses `handleAuth()` from `@workos-inc/authkit-nextjs` to exchange code for tokens and create session

**Tenant Login Flow** (AuthKit Hosted UI — same as admin):

- Tenant clicks "Sign in with Google" on tenant-facing pages (e.g., to save favorites or submit a visit request)
- Same `getSignInUrl()` → WorkOS hosted AuthKit → Google SSO → `/callback` flow as admin
- Differentiation: callback route receives a `user_type` hint via state parameter. If `user_type=TENANT`, the `user.created` event handler creates the Convex user record with `user_type: TENANT`.
- On success: redirect back to the tenant page they came from

**Owner Login Flow** (AuthKit Hosted UI — ops-initiated):

- Owners do NOT self-register. Ops team creates the owner's WorkOS account during onboarding (similar to guard account creation, but using the owner's real Google email instead of a synthetic email).
- After account creation, owner can sign in with Google on the owner portal.
- The `user.created` event handler detects `user_type=OWNER` from the creation metadata and creates the Convex user with `user_type: OWNER`.
- V1 owner authenticated experience is minimal (property status check only).

**Auth Method Summary**:

| Persona   | Auth Method                        | Login Page                              | WorkOS Flow                  | Synthetic Email Domain       |
| --------- | ---------------------------------- | --------------------------------------- | ---------------------------- | ---------------------------- |
| Guard     | Phone + password (synthetic email) | `/guard/login` (custom UI)              | `authenticateWithPassword()` | `{phone}@guards.local`     |
| OPS Agent | Phone + password (synthetic email) | `/ops/login` (custom UI)                | `authenticateWithPassword()` | `{phone}@ops.local` |
| Admin     | Google SSO                         | `/admin/login` → AuthKit hosted         | `getSignInUrl()` → callback  | —                            |
| Tenant    | Google SSO                         | Inline on tenant pages → AuthKit hosted | `getSignInUrl()` → callback  | —                            |
| Owner     | Google SSO (ops-created account)   | `/owner/login` → AuthKit hosted         | `getSignInUrl()` → callback  | —                            |

**No shared login page.** Guards and OPS agents use phone+password with synthetic emails. Admins, tenants, and owners use Google SSO only.

**OPS Login Flow** (Custom UI — same pattern as Guard):

- OPS agent enters **phone number + password** on `/ops/login`
- Next.js Server Action converts phone to synthetic email (`{phone}@ops.local`)
- Server Action calls `getWorkOS().userManagement.authenticateWithPassword({ email, password })`
- On success: `saveSession()` stores the session cookie → redirect to `/ops/dashboard`
- OPS layout checks `user_type === "OPS"` and `status === "ACTIVE"` (via `requireOps()` in `auth.helpers.ts`)

**Security**:

- Light browser fingerprinting on guard login (log browser/IP)
- Flag suspicious changes (new browser, unusual IP) for admin review
- No device binding in V1 (web-only, session-based auth is sufficient)

**Post-auth route checking** (in layouts, not middleware):

- Guard layout: queries Convex for user record, checks `user_type === "GUARD"` and `status !== "BANNED"`
- OPS layout: queries Convex for user record, checks `user_type === "OPS"` and `status === "ACTIVE"` (via `requireOps()`)
- Admin layout: queries Convex for user record, checks `user_type === "ADMIN"`
- Guard layout also checks `must_change_password` — if true, all routes except `/guard/change-password` redirect there

**Password change gate**: The guard layout component checks `must_change_password`. If true, redirect to `/guard/change-password`. After successful password change (via Next.js Server Action calling `getWorkOS().userManagement.updateUser()`), the flag is flipped to `false` and guard proceeds normally.

```typescript
// convex/auth.ts — AuthKit component + event handlers
import { AuthKit, type AuthFunctions } from "@convex-dev/workos-authkit";
import { components, internal } from "./_generated/api";
import type { DataModel } from "./_generated/dataModel";

const authFunctions: AuthFunctions = internal.auth;

export const authKit = new AuthKit<DataModel>(components.workOSAuthKit, {
  authFunctions,
});

export const { authKitEvent } = authKit.events({
  "user.created": async (ctx, event) => {
    const isGuard = event.data.email.endsWith("@guards.local");
    const isOps = event.data.email.endsWith("@ops.local");
    await ctx.db.insert("users", {
      workos_user_id: event.data.id,
      email: event.data.email,
      name: `${event.data.firstName ?? ""} ${event.data.lastName ?? ""}`.trim(),
      user_type: isGuard ? "GUARD" : isOps ? "OPS" : "ADMIN",
      status: "ACTIVE",
      must_change_password: isGuard || isOps, // Guards and OPS agents must change temp password
    });
  },
  "user.updated": async (ctx, event) => {
    const user = await ctx.db
      .query("users")
      .withIndex("by_workos_user_id", (q) => q.eq("workos_user_id", event.data.id))
      .unique();
    if (user) {
      await ctx.db.patch(user._id, {
        email: event.data.email,
        name: `${event.data.firstName ?? ""} ${event.data.lastName ?? ""}`.trim(),
      });
    }
  },
});
```

```typescript
// src/components/ConvexClientProvider.tsx
"use client";
import { ReactNode, useCallback, useState, useRef, useEffect } from "react";
import { ConvexReactClient } from "convex/react";
import { ConvexProviderWithAuth } from "convex/react";
import { AuthKitProvider, useAuth, useAccessToken } from "@workos-inc/authkit-nextjs/components";

export function ConvexClientProvider({ children }: { children: ReactNode }) {
  const [convex] = useState(() => new ConvexReactClient(process.env.NEXT_PUBLIC_CONVEX_URL!));
  return (
    <AuthKitProvider onSessionExpired={() => {}}>
      <ConvexProviderWithAuth client={convex} useAuth={useAuthFromAuthKit}>
        {children}
      </ConvexProviderWithAuth>
    </AuthKitProvider>
  );
}

function useAuthFromAuthKit() {
  const { user, loading: isLoading } = useAuth();
  const { getAccessToken, accessToken, refresh } = useAccessToken();
  const accessTokenRef = useRef<string | undefined>(undefined);
  useEffect(() => { accessTokenRef.current = accessToken; }, [accessToken]);
  const isAuthenticated = !!user;
  const fetchAccessToken = useCallback(
    async ({ forceRefreshToken }: { forceRefreshToken?: boolean } = {}): Promise<string | null> => {
      if (!user) return null;
      try {
        return forceRefreshToken ? ((await refresh()) ?? null) : ((await getAccessToken()) ?? null);
      } catch {
        return accessTokenRef.current ?? null;
      }
    },
    [user, getAccessToken, refresh],
  );
  return { isLoading, isAuthenticated, fetchAccessToken };
}
```

## Convex Database

### Why Convex

- **Reactive**: Real-time subscriptions out of the box. Admin panel auto-updates when guard submits a lead.
- **TypeScript-native**: Schema → queries → mutations → frontend — all type-safe.
- **Serverless functions**: No separate API layer. Convex functions ARE the API.
- **File storage**: Built-in. No S3/Cloudinary needed for listing photos and documents.
- **Auth integration**: First-class WorkOS support.

### Convex Patterns Used

- **Schema definitions**: Typed tables with validators
- **Queries**: Read-only, reactive, auto-subscribe in React
- **Mutations**: Write operations, transactional
- **Actions**: For side effects (external API calls, file processing)
- **File storage**: Upload via `storage.generateUploadUrl()`, serve via `storage.getUrl()`
- **Indexes**: For efficient queries (e.g., leads by society, guards by society)

### Auth Helpers (`convex/auth.helpers.ts`)

- `getAuthenticatedUser(ctx)`: Uses `authKit.getAuthUser(ctx)` to get WorkOS user, then looks up our `users` table by `workos_user_id`. Returns the Convex user record or `null`.
- `requireAuth(ctx)`: Requires an authenticated user and rejects when user status is `BANNED`.
- `requireGuard(ctx)`: Requires `user_type === "GUARD"` and `status === "ACTIVE"`.
- `requireAdmin(ctx)`: Requires `user_type === "ADMIN"` (no status check; admins are removed, not banned).
- `requireOps(ctx)`: Requires `user_type === "OPS"` and `status === "ACTIVE"`. Used in OPS portal layouts and OPS-specific mutations.
- `requireBackoffice(ctx)`: Requires `user_type === "ADMIN"` or `user_type === "OPS"`, plus `status === "ACTIVE"`. Used for shared backoffice read paths — system config, user lookups, role assignment queries. For admin-only management, use `requireAdmin()`.
- `requirePermission(ctx, permission)`: Loads role assignments from `user_role_assignments`, unions all role permissions, and verifies the requested permission exists. Accepts **both** `user_type === "ADMIN"` and `user_type === "OPS"` — OPS agents share the same RBAC system as admins with zero mutation duplication.

### Convex Actions (External API Calls)

Convex queries and mutations **cannot** call external APIs. Actions can. WorkOS user management operations go through Convex Actions:

- `createGuardAccount({ name, phone, society_id, guard_type, temp_password })`: Creates the WorkOS user (via `workos.userManagement.createUser()`), then the `user.created` webhook event handler auto-creates Convex `users` + triggers guard_profiles creation.
- `resetGuardPassword({ workos_user_id, new_temp_password })`: Calls `workos.userManagement.updateUser()` to set a temporary password and sets `must_change_password = true` in Convex.
- `suspendGuard({ workos_user_id, user_id, reason })`: Calls `workos.userManagement.updateUser({ status: "suspended" })`, sets Convex user status to `BANNED`, and flags pending visits for reassignment.
- `unsuspendGuard({ workos_user_id, user_id, new_status })`: Reactivates the WorkOS account and updates Convex user status.

**Guard password change** uses a **Next.js Server Action** (not Convex Action) because it needs to call `saveSession()` to refresh the session cookie after password change. The Server Action calls `getWorkOS().userManagement.updateUser()` directly.

**Error handling**: If WorkOS call succeeds but Convex mutation fails (or vice versa), the action should retry the failed step. If both fail, surface the error to the UI. No silent partial failures.

### Convex HTTP Router (Public Endpoints)

For server-rendered public listing pages, Convex exposes an HTTP endpoint:

```typescript
// convex/http.ts
import { httpRouter } from "convex/server";

const http = httpRouter();

// Public listing data endpoint — called by Next.js Server Components for SSR
http.route({
  path: "/api/listing/:slug",
  method: "GET",
  handler: async (ctx, request) => {
    const slug = request.pathParams.slug;
    const listing = await ctx.runQuery(internal.listings.getBySlugInternal, { slug });
    if (!listing) return new Response("Not found", { status: 404 });
    return Response.json(listing);
  },
});

export default http;
```

**Why HTTP Router instead of `fetchQuery`**: The HTTP endpoint is cacheable, doesn't require Convex client setup on the server, and works cleanly with Next.js ISR/SSR. The Server Component fetches listing data from this endpoint, then passes it to client components for hydration with real-time subscriptions.

**Photo URLs**: Server Component resolves `storage_id` → URL separately via Convex's `storage.getUrl()` (called from a Server Action or API route). Not included in the HTTP endpoint response.

### Function Wrapper Pattern

All domain files import and re-export queries/mutations via `convex/functions.ts`. Mutations are wrapped with `customMutation(rawMutation, customCtx(triggers.wrapDB))` (and the same wrapper pattern for internal mutations), so trigger middleware runs consistently. Direct mutation imports from `_generated/server` are blocked by an ESLint `no-restricted-imports` rule to prevent bypassing wrappers. This is what enables automatic audit logging on business tables. See [Convex Architecture](11-convex-architecture.md) for implementation details.

### Soft Delete Convention

Entities that use `is_deleted: boolean` instead of hard delete: `buildings`, `guard_shifts`, `roles`, `user_role_assignments`, `listing_photos`. Every query MUST filter `is_deleted !== true`. See [Convex Architecture](11-convex-architecture.md) for the filter pattern.

### Audit Logging

Audit logging is trigger-based and automatic. Mutations on business tables create `audit_logs` entries without manual logging code in domain mutations. Log records capture actor, action, entity, field-level changes, and metadata. See [Audit Trail](07-audit-trail.md) for viewer spec, [Convex Architecture](11-convex-architecture.md) for trigger implementation.

### Rate Limiter

- `guard:lead_submission`: Fixed window, 24 hours, default 5/day (overridden by `system_config.max_leads_per_guard_per_day`).
- `public:listing_inquiry`: Fixed window, 1 hour, 5 inquiries per IP.

Uses the `@convex-dev/rate-limiter` component. See [Convex Schema](10-convex-schema.md) for configuration.

### Cron Jobs

- `daily-analytics-snapshot`: Runs daily at 12:30 AM IST (19:00 UTC), calls `internal.analytics.computeDailySnapshot`.
- `recover-stale-chat-batches`: Runs every 5 minutes, calls `internal.chatBatching.recoverStaleBatches`. Recovers chat message batches stuck in `COLLECTING` or `PROCESSING` state.
- Rate limit counter reset is handled automatically by the rate-limiter component.

See [Convex Schema](10-convex-schema.md) for cron configuration.

### Component Registration

`convex/convex.config.ts` registers:

- `@convex-dev/workos-authkit` (user sync + webhook handling)
- `@convex-dev/rate-limiter`
- `@convex-dev/aggregate` with named instances: `leadCounts`, `visitCounts`, `payoutTotals`

See [Convex Schema](10-convex-schema.md) for full config.

### De-duplication Logic

Lead submission uses `checkDuplicates()` before insert:

- Rule 1: Same flat (`society + building + flat_number`) within 90 days flags `DUPLICATE_FLAT_MATCH`.
- Rule 2: Same owner phone in the same society within 30 days flags `DUPLICATE_PHONE_MATCH`.
- Window values are configurable via `system_config` keys: `dedup_flat_window_days`, `dedup_phone_window_days`.
- Existing leads with status `REJECTED` or `DUPLICATE` are excluded from duplicate matching.

See [Convex Architecture](11-convex-architecture.md) for implementation.

## Frontend Architecture

### Next.js App Router

- **Route Groups**: `(guard)`, `(admin)`, `(ops)`, `(tenant)`, and `(public)` for role-based and persona-based layouts
  - `(ops)/` — OPS portal layout with `requireOps()` auth check. Mobile-first. OPS agents log in at `/ops/login` with phone+password (synthetic email `{phone}@ops.local`). All OPS portal pages live under `(ops)/ops/` (route group + real directory pattern, same as guard/admin). See [Auth Architecture](#authentication-architecture) for the OPS login flow.
- **Middleware**: WorkOS `authkitMiddleware()` for route protection
- **Server Components**: For initial data fetch where possible
- **Client Components**: For interactive UI with Convex real-time subscriptions

### shadcn/ui + Tailwind

- **Admin Panel**: Data tables, forms, dialogs, command palette, toasts
- **Guard Portal**: Cards, buttons, badges, simple forms — all mobile-first
- **Theming**: Tailwind CSS variables (oklch), light mode only
- **Responsive**: Mobile-first for guard portal, desktop-first for admin
- **Form inputs**: DatePicker, TimePicker, Select, Checkbox, RadioGroup, Textarea, Input — all shadcn/ui-based, no native HTML form elements

**Theme**: `next-themes` is configured with `defaultTheme="light"` and `enableSystem={false}` — the app renders in light mode only. Dark mode is not in V1 scope.

### Tailwind v4 + shadcn/ui

As of 2026, shadcn/ui uses **Tailwind v4** which changes theming:

- **No `tailwind.config.ts` required** — theming via CSS `@theme inline` directive in `globals.css`
- Colors use **oklch** color space for perceptually uniform gradients
- Component style: **"new-york"** variant (smaller, refined — premium feel)
- Font: **Geist Sans** (body) + **Geist Mono** (code/IDs/phones)
- Border radius: `0.5rem` (8px) base — crisp, modern

### i18n Architecture

- Three locales: `en` (English), `hi` (Hindi), `hinglish` (Hinglish)
- Use `next-intl` or similar i18n library with Next.js App Router
- Translation files: JSON per locale
- Language selector on guard portal (persistent preference)
- Admin panel: English only (ops team is English-literate)
- Guard portal: All three options, selectable on first login

## Bootstrap / Seed

On first deployment, run the seed function to create default roles and the first super-admin:

```bash
npx convex run seed:init
```

```typescript
// convex/seed.ts
// Internal mutation — run once on first deployment via CLI

// 1. Check if roles table is empty (idempotent — skip if already seeded)
// 2. Create "Super Admin" role (all permissions, is_system_role: true)
// 3. Create "Ops Agent" role (operational permissions, is_system_role: true)
// 4. Read SUPER_ADMIN_EMAIL from environment variable
// 5. Call WorkOS createUser() with that email (via Action)
// 6. Create Convex user record (user_type: ADMIN, status: ACTIVE)
// 7. Assign Super Admin role to the user
// 8. Create default system_config entries (rate limits, thresholds, etc.)
```

**Environment variable**: `SUPER_ADMIN_EMAIL` — the Google email of the first super admin. Set in Convex dashboard environment variables.

**Idempotent**: Running seed multiple times is safe — it checks for existing data before creating.
