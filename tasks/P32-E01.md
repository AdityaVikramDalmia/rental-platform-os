# P32-E01: Core Engine + Config Versioning

## Summary

Establish the Incentive v3 foundation: persona-aware actor profiles, versioned incentive configs, rollout controls, shadow delta persistence, and an `/admin/incentive-settings` shell. This epic creates the minimum platform surface required for commission, attribution, and gamification work in subsequent epics while keeping v2 behavior as the baseline.

**Sizing split**: Task system cap is 8 tasks per epic. Execute as two batches: Batch A (T01-T08), Batch B (T09-T16).

## Tasks

### T01: Schema - Incentive Persona and Actor Profiles

**Description**: Add persona validators and `incentive_actor_profiles` table with indexes for user and persona-active lookups.

**Acceptance Criteria**:

1. Validator supports all required v3 incentive personas.
2. `incentive_actor_profiles` stores assignment, rate bounds, active window, and admin updater fields.
3. Indexes support `by_user` and `by_persona_active` access patterns.

**Estimated Effort**: M (0.5 day)

### T02: Schema - Config Versions Table

**Description**: Add `incentive_config_versions` for versioned `DRAFT -> ACTIVE -> ARCHIVED` lifecycle and immutable snapshots.

**Acceptance Criteria**:

1. Table includes version code, status, config JSON, optimizer bounds JSON, and activation metadata.
2. Indexes support `by_version` and `by_status`.
3. Lifecycle fields support publish/archive workflow.

**Estimated Effort**: S (0.25 day)

### T03: Constants - Core V3 Enums

**Description**: Add typed constants for persona, contribution stage, attribution algorithm, config version status, v3 permissions, and role seeding defaults.

**Acceptance Criteria**:

1. Four enum groups exported with inferred TypeScript union types.
2. Names and literal values align with v3 feature docs.
3. Existing constants remain backward compatible.
4. Add `commission.configure`, `commission.view`, `attribution.override`, `attribution.view`, `gamification.manage`, `gamification.view`, `shadow_mode.manage`, `disbursement.approve`, and `disbursement.void` in `lib/constants.ts`.
5. Seed these permissions into default role mappings so admin/ops role grants are available immediately after seed.
6. Permission strings must match dot-notation pattern used in `lib/constants.ts` `PERMISSIONS` object (e.g., `leads.manage`, `visits.manage`).

**Estimated Effort**: S (0.25 day)

### T04: System Config Keys - Runtime Pointers

**Description**: Register v3 runtime control keys in system config defaults and constants.

**Acceptance Criteria**:

1. Keys exist for active config version, feature flags, and rollout policy.
2. Seed/default values are valid JSON payloads for runtime reads.
3. Keys are discoverable in admin config surfaces.

**Estimated Effort**: S (0.25 day)

### T05: Backend - Config Version CRUD

**Description**: Implement `convex/incentiveConfig.ts` with create-draft, update-draft, activate, and archive operations; runtime evaluators must read active config snapshots from version rows.

**Acceptance Criteria**:

1. Draft updates blocked for non-draft versions.
2. Activation atomically updates active pointer and status transitions.
3. Archive flow preserves historical versions without hard delete.
4. Source-of-truth rule is enforced: evaluation time reads from active `incentive_config_versions.config_json` snapshot and never from `commission_modifier_templates` directly.

**Estimated Effort**: M (0.5 day)

### T06: Backend - Actor Profile CRUD

**Description**: Implement `convex/incentiveActors.ts` to assign persona tracks, update rates, and list actors by persona.

**Acceptance Criteria**:

1. Admin can assign/update actor persona profiles with effective windows.
2. Query supports filtering by persona and active flag.
3. Mutations enforce permission and type-safe payload validation.

**Estimated Effort**: M (0.5 day)

### T07: Seed - Initial v3 Config

**Description**: Seed `v3.0.0` baseline config that mirrors v2 economics for shadow-mode parity checks.

**Acceptance Criteria**:

1. Seed is idempotent and does not duplicate version records.
2. Config defaults preserve v2-equivalent payout behavior.
3. Version is available as a draft/initial active candidate per rollout policy.

**Estimated Effort**: S (0.25 day)

### T08: Admin UI - Settings Shell

**Description**: Add `/admin/incentive-settings` route with tabbed layout for Program, Personas, Commission, Attribution, Gamification.

**Acceptance Criteria**:

1. Route is permission-gated in admin portal.
2. All 5 tabs render shell states without runtime errors.
3. Page integrates with existing admin layout and navigation patterns.

**Estimated Effort**: M (0.5 day)

### T09: Admin UI - Program Tab

**Description**: Implement active version display, feature flag controls, and rollout policy editor.

**Acceptance Criteria**:

1. Active config version is visible and refreshes from backend state.
2. Feature flags can be toggled and persisted.
3. Rollout policy selection persists in system config.

**Estimated Effort**: M (0.5 day)

### T10: Admin UI - Personas Tab

**Description**: Implement actor profile table, persona assignment dialog, and track config editing.

**Acceptance Criteria**:

1. Persona table lists actor profiles with active windows and rate bounds.
2. Assignment dialog creates/updates persona track entries.
3. Admin can filter by persona and view current track config.

**Estimated Effort**: M (0.5 day)

### T11: Audit Trail Wiring - v3 Entities and Actions

**Description**: Extend audit wiring for new v3 entities and action taxonomy in the wrapped Convex function layer.

**Acceptance Criteria**:

1. New v3 tables are included in audited table mappings in `convex/functions.ts`.
2. Audit action constants exist for commission evaluation, attribution, disbursement, config activation, and modifier template changes.
3. Mutations touching these entities emit traceable audit events with actor and entity metadata.

**Estimated Effort**: S (0.25 day)

### T12: State Machine Documentation - Incentive v3 Lifecycles

**Description**: Document Incentive v3 lifecycle transitions in `notes/04-state-machines.md` for config, attribution, and disbursement flows.

**Acceptance Criteria**:

1. Transition tables are added for `incentive_config_versions`, `attribution_records`, and `incentive_disbursements`.
2. Attribution lifecycle docs use `PROVISIONAL -> FINAL -> DISPUTED -> RESOLVED`, and this task updates `notes/04-state-machines.md` from legacy `DRAFT`/`OVERRIDDEN` labels to `PROVISIONAL`/`RESOLVED` terminology.
3. Allowed transitions include publish/archive for config versions, dispute/resolution flow for attribution records, and approve/disburse/void guards for disbursements.
4. Transition docs align with enum constants used in implementation tasks.

**Estimated Effort**: S (0.25 day)

### T13: Property Tests - Core Engine and Config Versioning

**Description**: Add property tests that stress deterministic behavior for core config and actor profile flows.

**Acceptance Criteria**:

1. Tests validate rounding correctness and deterministic outputs across randomized valid inputs.
2. Retry/idempotency behavior is verified for repeated activate/update operations.
3. Edge cases include zero profit, single-contributor scenarios, and all modifiers disabled fallback.

**Estimated Effort**: M (0.5 day)

### T14: Schema - Shadow Mode Delta Ledger

**Description**: Add `shadow_mode_deltas` as the canonical per-deal parity ledger for v2 vs v3 outputs.

**Acceptance Criteria**:

1. Table includes `deal_id`, `entity_type`, `persona: v.optional(incentivePersonaValidator)`, `config_version_id: v.optional(v.id("incentive_config_versions"))`, `v2_result_json`, `v3_result_json`, `delta_summary`, and `created_at`.
2. `entity_type` validator supports `commission`, `attribution`, and `disbursement`.
3. Indexes exist for `by_deal` and `by_entity_type` with key order `["entity_type", "persona", "created_at"]`.

**Estimated Effort**: S (0.25 day)

### T15: One-Time Migration Action - v2 to v3 Bootstrap

**Description**: Build one-time Convex action for migration bootstrap and controlled rollback, using `source_type: "V2_MIGRATION"` for migrated disbursement rows.

**Acceptance Criteria**:

1. Action seeds `gamification_profiles` from `quality_score_history` and `guard_streaks`.
2. Action creates `incentive_disbursements` from confirmed `incentive_cards` with deterministic mapping.
3. Migration is idempotent and safe to re-run.
4. Rollback capability exists to revert migrated rows by migration run identifier.
5. The `V2_MIGRATION` literal must be added to the `incentive_disbursements.source_type` validator in `convex/schema.ts`.

**Estimated Effort**: M (0.5 day)

### T16: Analytics Contracts - Incentive v3 Query Surface

**Description**: Define analytics query contracts needed by v3 admin reporting and rollout validation.

**Acceptance Criteria**:

1. `convex/analytics.ts` exports `getCommissionTrends`, `getAttributionFairness`, `getGamificationEngagement`, `getModifierEffectiveness`, `getShadowModeDelta`, and `getPersonaEarnings`.
2. Query args/returns are typed and documented for admin UI consumption.
3. `getShadowModeDelta` reads from `shadow_mode_deltas` as its source table.

**Estimated Effort**: M (0.5 day)
