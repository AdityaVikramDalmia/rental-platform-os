# P32-E02: Commission Engine

## Summary

Build the dynamic commission computation engine for Incentive v3, including performance modifier logic, closure-triggered shadow evaluation, admin configuration surfaces, and OPS transparency views. This epic introduces deterministic per-deal commission records while keeping v2 payout as source of truth during rollout.

> All V3 table schemas are canonically defined in F24 (`notes/features/24-incentive-v3-overview.md`). Tasks in this epic reference those schemas - do not redefine table structures.

**Sizing split**: Task system cap is 8 tasks per epic. Execute as two batches: Batch A (T01-T08), Batch B (T09-T14).

## Tasks

### T01: Schema - Commission Evaluations

**Description**: Add `deal_commission_evaluations` as the canonical per-closure commission output table.

**Acceptance Criteria**:

1. Table stores base/effective rates, profit input, pool amount, `config_version`, `config_snapshot`, modifier breakdown, and evaluation status.
2. Indexes support fetch by closure and actor time-series views.
3. All amount fields are integer paise.
4. Each `modifier_breakdown` item includes `template_id`, `template_name`, `reward_mode` (`BPS`/`FLAT_PAISE`), optional `delta_bps`, optional `delta_paise`, `link_mode`, optional `link_group_id`, and `passed`.
5. `deal_commission_evaluations` persists `config_version` and `config_snapshot` on every record so downstream attribution/disbursement reads config from this record.

**Estimated Effort**: M (0.5 day)

### T02: Constants - Modifier Types and Defaults

**Description**: Define rule types (`threshold_step`, `linear_band`, `penalty_step`) and default modifier set in constants/config.

**Acceptance Criteria**:

1. Modifier type enums and operators are exported with inferred TS types.
2. Default modifier config includes required metrics and deltas.
3. Bounds preserve base range 1500-2200 bps.
4. Persona-scoped defaults include explicit `ALL` fallback entries where persona-targeted modifiers are resolved.

**Estimated Effort**: S (0.25 day)

### T03: Backend - Commission Engine API

**Description**: Implement core commission engine module with evaluate/query/simulate methods, mixed modifier composition support, and canonical pool computation.

**Acceptance Criteria**:

1. `evaluate()` computes and persists latest evaluation using the canonical formula:
   ```
   pool = max(0, floor(profit × effective_rate_bps / 10000) + flat_bonus_paise)
   ```
2. `getEvaluation()` returns latest non-deleted record by closure.
3. `getMyCommissionBreakdown()` returns OPS-facing summary and recent evaluations.
4. `simulateEvaluation()` runs dry mode without writes.
5. Evaluation supports both BPS and FLAT_PAISE modifiers, including AND_GROUP/OR_GROUP composition logic.
6. API responses return typed `modifier_breakdown` items with the required contract fields (`template_id`, `template_name`, `reward_mode`, `delta_bps?`, `delta_paise?`, `link_mode`, `link_group_id?`, `passed`).
7. Every persisted evaluation writes `config_version` and `config_snapshot`; downstream attribution/disbursement must read these fields from `deal_commission_evaluations`, not from active `incentive_config_versions`.

**Estimated Effort**: L (1 day)

### T04: Backend - Metric Computation Functions

**Description**: Implement metric collectors for document speed, punctuality, checklist quality, response speed, completeness, and penalty metrics.

**Acceptance Criteria**:

1. Metrics compute from existing operational tables with deterministic windows.
2. Low-data windows flag limited-data explanations.
3. Metric outputs are reusable by both evaluate and simulation flows.

**Estimated Effort**: L (1 day)

### T05: Integration - Closure Trigger (Shadow Mode)

**Description**: Trigger v3 commission evaluation when closure is confirmed while preserving v2 payout behavior.

**Acceptance Criteria**:

1. Every eligible closure confirmation runs commission evaluation.
2. Evaluation write failures are visible/auditable and do not corrupt closure state transition.
3. Payout amounts continue to source from v2 during shadow mode.

**Estimated Effort**: M (0.5 day)

### T06: Admin UI - Commission Tab

**Description**: Build commission settings UI in `/admin/incentive-settings` with base-rate controls and editable modifier rules.

**Acceptance Criteria**:

1. Admin can add/edit/enable/disable modifiers.
2. Base range controls validate floor/ceiling constraints.
3. Changes are saved into draft config versions only.

**Estimated Effort**: M (0.5 day)

**Acceptance Criteria**:

**Estimated Effort**: M (0.5 day)

**Description**: Embed transparency card in OPS dashboard and/or earnings experience.

**Acceptance Criteria**:

3. Empty/no-evaluation states are handled gracefully.

**Estimated Effort**: S (0.25 day)

### T09: Backend - Simulation Engine

**Description**: Implement closure-picked simulation that compares v3 outcome against v2 payout baseline.

**Acceptance Criteria**:

1. Simulation returns effective rate, pool, and variance vs v2.
2. Simulation can target active or selected config version.
3. Simulation leaves no persistent side effects.
4. Simulation pool math uses the same canonical formula as evaluation:
   ```
   pool = max(0, floor(profit × effective_rate_bps / 10000) + flat_bonus_paise)
   ```

**Estimated Effort**: M (0.5 day)

### T10: Admin UI - Simulation Tab

**Description**: Add simulation tab workflow in `/admin/incentive-settings` for closure selection and side-by-side results.

**Acceptance Criteria**:

1. Admin can run simulation from UI for a selected closure.
2. Results show v3 rate, v2 payout, and delta clearly.
3. Simulation output is read-only and traceable.
4. Backend query contracts exist for evaluation window listing, variance summary, and modifier hit-rate reporting.

**Estimated Effort**: M (0.5 day)

### T11: Schema - Commission Modifier Templates

**Description**: Add reusable modifier template storage for persona-scoped commission logic, including global fallback templates.

**Acceptance Criteria**:

1. `commission_modifier_templates` exists in `convex/schema.ts` with persona, reward mode, rule config, and lifecycle fields.
2. Indexes support list-by-persona and active-template lookup patterns.
3. Template rows are auditable and compatible with config version snapshots.
4. Persona validator supports `GUARD`, `OPS`, `SALES`, `RM`, `LIAISON`, and `ALL`.
5. Persona enum remains canonical; stage is modeled as a separate field and must not be encoded in persona literals (no suffix values like `GUARD_DISCOVERY` or `OPS_EXECUTION`).

**Estimated Effort**: S (0.25 day)

### T12: Backend - Modifier Template CRUD

**Description**: Implement `convex/commissionModifierTemplates.ts` for create, update, archive, and persona-filtered listing.

**Acceptance Criteria**:

1. CRUD APIs validate `reward_mode` and rule payload shape.
2. Archive flow is non-destructive and excludes archived templates by default.
3. APIs are permission-gated (`commission.configure` for create/update/archive, `commission.view` for listing) and return typed payloads for Commission tab usage.
4. Persona-filtered list APIs accept `ALL` as a valid filter and include fallback templates when requested.

**Estimated Effort**: M (0.5 day)

### T13: Admin UI - Modifier Template Editor

**Description**: Build modifier template editor in the Commission tab using create/edit dialog flows.

**Acceptance Criteria**:

1. Dialog supports `reward_mode` values BPS and FLAT_PAISE.
2. Admin can set `rule_type`, `metric_source`, and `link_mode` (AND/OR/INDIVIDUAL).
3. Editor supports create and update without mutating active config outside draft workflow.

**Estimated Effort**: M (0.5 day)

### T14: Property Tests - Commission Engine

**Description**: Add property tests for deterministic commission computations across varied modifier states.

**Acceptance Criteria**:

1. Tests prove rounding correctness for paise-level outputs.
2. Retry/idempotency tests confirm no duplicate side effects on repeated evaluate/disburse triggers.
3. Edge-case coverage includes zero profit, single contributor, and all modifiers disabled.

**Estimated Effort**: M (0.5 day)
