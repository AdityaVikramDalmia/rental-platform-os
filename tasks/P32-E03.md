# P32-E03: Multi-Contributor Attribution

## Summary

Implement event-driven contribution logging and deterministic attribution splitting for multi-actor deals. This epic materializes contribution ledger entries, attribution records/splits, disbursement workflows, and admin/operator visibility, including a dispute and resolution path.

> All V3 table schemas are canonically defined in F24 (`notes/features/24-incentive-v3-overview.md`). Tasks in this epic reference those schemas - do not redefine table structures.

**Sizing split**: Task system cap is 8 tasks per epic. Execute as two batches: Batch A (T01-T08), Batch B (T09-T14).

## Tasks

### T01: Schema - Attribution Core Tables

**Description**: Add contribution, attribution record, and attribution split tables with lifecycle fields and query indexes.

**Acceptance Criteria**:

1. `deal_contributions`, `attribution_records`, and `attribution_splits` exist with required validators.
2. Indexes support queries by closure, actor, attribution record, and status.
3. Soft-delete conventions are respected where applicable.
4. `deal_contributions` includes `event_key: v.string()` with format `{closure_id}:{stage}:{user_id}:{action_type}` and index `by_event_key`.
5. `attribution_records.status` uses canonical lifecycle literals: `PROVISIONAL`, `FINAL`, `DISPUTED`, `RESOLVED`.

**Estimated Effort**: M (0.5 day)

### T02: Backend - Contribution Logger

**Description**: Create internal mutation to append normalized contribution events.

**Acceptance Criteria**:

1. `logContribution()` validates stage/persona/source entity contract.
2. Writes are append-only and timestamped.
3. Logger is reusable by lead/visit/closure flows.
4. Before insert, logger checks `by_event_key`; if key already exists, skip write for idempotent retries.

**Estimated Effort**: S (0.25 day)

### T03: Integration - Automatic Contribution Hooks

**Description**: Wire contribution logging to existing action events.

**Acceptance Criteria**:

1. `leads.submit` logs `DISCOVERY` contribution.
2. `visits.complete` logs `VERIFICATION` contribution.
3. `closures.confirm` logs `CLOSURE` contribution.

**Estimated Effort**: M (0.5 day)

### T04: Integration - Handoff Tracking

**Description**: Track reassignment handoffs as explicit SUPPORT-stage contribution events.

**Acceptance Criteria**:

1. Reassignment writes `SUPPORT` stage contributions.
2. Event stores `handoff_from_user_id` and handoff reason metadata.
3. Handoff records are attributable in later split computation.
4. `FOLLOW_UP` activities are classified under the `SUPPORT` stage.

**Estimated Effort**: S (0.25 day)

### T05: Backend - Attribution Algorithm

**Description**: Implement `computeAttribution()` using `STAGE_WEIGHTED_QUALITY_V1`, stage-first allocation, and closure-pinned commission evaluation config.

**Acceptance Criteria**:

1. Function consumes closure contributions and commission pool.
2. Profit pool is first divided into stage buckets by weight: `DISCOVERY` 25%, `VERIFICATION` 35%, `CLOSURE` 25%, `SUPPORT` 15%.
3. Within each stage bucket, amounts split among contributors using quality-weighted scores.
4. Attribution evaluation MUST read config from the `deal_commission_evaluations` record for the closure (fields: `config_version`, `config_snapshot`), NOT from the active `incentive_config_versions` record. This prevents mid-pipeline config drift.
5. Result persists attribution record plus `PROVISIONAL` splits.
6. If a stage has zero contributors, its budget is redistributed proportionally to non-empty stages. If ALL stages are empty, no disbursement is created (pool held in reserve).

**Estimated Effort**: L (1 day)

### T06: Math - Largest Remainder Rounding

**Description**: Guarantee split amounts sum exactly to pool paise.

**Acceptance Criteria**:

1. Rounding algorithm is deterministic and stable across retries.
2. Sum of all split rows equals pool amount exactly.
3. Tie-break rules are explicit and reproducible.

**Estimated Effort**: S (0.25 day)

### T07: Schema - Incentive Disbursements

**Description**: Add disbursement ledger table for attribution-based payments and future reward types.

**Acceptance Criteria**:

1. Table supports source linkage (`ATTRIBUTION_SPLIT`, `QUEST_REWARD`, `TEAM_POOL`).
2. Status lifecycle supports pending/approved/disbursed/failed/voided.
3. Indexes support recipient and closure lookups.
4. `incentive_disbursements` includes `source_key: v.string()` with format `{source_type}:{source_record_id}` and index `by_source_key`.

**Estimated Effort**: S (0.25 day)

### T08: Backend - Disbursement Lifecycle

**Description**: Implement disbursement module to materialize payouts from splits and run admin lifecycle actions.

**Acceptance Criteria**:

1. Disbursement rows can be created from `FINAL` attribution splits.
2. Approve/disburse/void transitions are validated.
3. Admin actions are auditable and permission-guarded (`disbursement.approve`, `disbursement.void`).
4. Before insert, disbursement creation checks `by_source_key`; if key already exists, skip write.

**Estimated Effort**: M (0.5 day)

### T09: Admin UI - Attribution Settings Tab

**Description**: Build controls in `/admin/incentive-settings` for stage weights and quality adjustment behavior.

**Acceptance Criteria**:

1. Stage weight controls must total exactly 100% before save.
2. Quality adjustment toggle persists to draft config.
3. Invalid weight mixes are blocked with clear validation.

**Estimated Effort**: M (0.5 day)

### T10: Admin UI - Attribution Viewer

**Description**: Build per-closure split visualization and traceability panel.

**Acceptance Criteria**:

1. Viewer shows contributors, stages, shares, and amount splits.
2. Admin can inspect computation metadata and config version used.
3. Viewer clearly marks `PROVISIONAL`, `FINAL`, `DISPUTED`, and `RESOLVED` states.
4. Query contracts exist for closure drill-down, dispute queue, and aggregate split distribution reporting.

**Estimated Effort**: M (0.5 day)

### T11: OPS/Guard UI - Attribution Earnings View

**Description**: Expose attribution-based earning breakdowns in operator-facing earnings pages.

**Acceptance Criteria**:

1. Users can see deal-level split amount and stage contribution context.
2. View is filtered to the authenticated user.
3. Historical split timeline supports pagination.

**Estimated Effort**: M (0.5 day)

### T12: Disputes and Resolution Flow

**Description**: Add admin tools to flag disputed attributions and resolve them with manual split adjustments.

**Acceptance Criteria**:

1. Admin can mark attribution records as disputed.
2. Admin can submit resolution splits with reason and audit metadata.
3. Status lifecycle follows `PROVISIONAL -> FINAL -> DISPUTED -> RESOLVED`.
4. Resolved output re-materializes disbursement source records cleanly.

**Estimated Effort**: M (0.5 day)

### T13: Integration - Support Contribution Hook

**Description**: Add SUPPORT-stage contribution logging when admin verification transitions a lead to `VERIFIED` through the `LEADS_UPDATE` action path.

**Acceptance Criteria**:

1. Admin verification flow writes a SUPPORT contribution event on valid `VERIFIED` transition.
2. Event payload links to lead/admin actor and remains idempotent across retried transition handlers.
3. SUPPORT contributions are visible to attribution computation and admin trace views.
4. Audit linkage uses `LEADS_UPDATE` (codebase action constant), not `LEAD_STATUS_CHANGE`.

**Estimated Effort**: S (0.25 day)

### T14: Property Tests - Attribution and Disbursement

**Description**: Add property tests for split math and lifecycle safety in attribution/disbursement flows.

**Acceptance Criteria**:

1. Tests validate deterministic largest-remainder rounding and exact pool conservation.
2. Retry/idempotency tests prevent duplicate contributions, splits, or disbursement side effects.
3. Edge cases include zero profit pools, single contributor attribution, and all modifiers disabled fallback paths.

**Estimated Effort**: M (0.5 day)

## Verification

1. Contributions are auto-logged on lead submit, visit complete, closure confirm, and admin verification to VERIFIED.
2. Attribution computes deterministic, exact-paise splits per closure.
3. Admin can view, dispute, and resolve attribution outcomes.
4. OPS/guard users can view their attribution shares in earnings surfaces.
