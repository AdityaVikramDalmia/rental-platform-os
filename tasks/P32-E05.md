## Tasks

### T01: Shadow Mode Runtime

**Description**: Runtime shadow evaluator: ensure all closure events trigger v3 computation while payout disbursement continues to follow v2 source of truth, and write per-closure delta rows.

**Acceptance Criteria**:

1. Every closure has corresponding v3 evaluation records in shadow mode.
2. Shadow evaluation never mutates current payout values.
3. Failures are visible via audit/logging and recoverable via replay.
4. Runtime shadow writes include parity rows in `shadow_mode_deltas` for `commission`, `attribution`, and `disbursement` entities.
5. Each runtime delta row captures primary `persona` and `config_version_id` when available.

**Estimated Effort**: M (0.5 day)

### T02: Delta Report Generation

**Description**: Compute and persist delta signals between v3 outputs and v2 paid amounts using `shadow_mode_deltas` as the reporting source.

**Acceptance Criteria**:

1. Delta records include absolute and percentage variance.
2. Deltas are attributable to `deal_id`, `config_version_id`, and evaluation timestamp.
3. Report reads persisted rows from `shadow_mode_deltas` (no ephemeral-only aggregation).

**Estimated Effort**: M (0.5 day)

### T03: Admin Delta Reporting UI

**Description**: Build admin views for closure-level and aggregate variance analysis.

**Acceptance Criteria**:

1. Admin can inspect per-closure v2 vs v3 breakdown.
2. Admin can view aggregate deltas across selectable time periods.
3. Views include filters for persona, status, and variance bands via `getShadowModeDelta` query.

**Estimated Effort**: M (0.5 day)

### T04: OPS/SALES Activation

**Description**: Enable v3 disbursement flow for non-guard personas while guard remains on compatibility mode.

**Acceptance Criteria**:

1. OPS/SALES disbursements can move through approval/disbursement lifecycle.
2. Activation is controlled by rollout policy and feature flags.
3. Existing guard payout flow remains unaffected.

**Estimated Effort**: M (0.5 day)

### T05: Guard Compatibility Mode

**Description**: Keep guard earnings sourced from v2 while v3 computes and reports in parallel.

**Acceptance Criteria**:

1. Guard payout amounts remain exactly v2-derived during compatibility period.
2. V3 records are still generated for every guard-eligible closure.
3. Compatibility mode is explicit in rollout policy state.

**Estimated Effort**: S (0.25 day)

### T06: Guard Migration Toggle

**Description**: Add admin-controlled toggle to switch guard payout source from v2 to v3.

**Acceptance Criteria**:

1. Toggle is gated by `shadow_mode.manage` and auditable.
2. Switching source does not break payout state machine.
3. Rollback path back to compatibility mode exists if required.

**Estimated Effort**: M (0.5 day)

### T07: Decommission v2 Shadow Path

**Description**: Remove transitional v2 shadow plumbing after two stable payout cycles.

**Acceptance Criteria**:

1. Decommission gate checks 2 completed cycles and acceptable variance thresholds.
2. Legacy shadow-only code paths are removed or disabled safely.
3. Historical data remains queryable for audit.

**Estimated Effort**: M (0.5 day)

### T08: Documentation Reconciliation

**Description**: Update phase and feature index documentation after rollout setup is complete.

**Acceptance Criteria**:

1. `AGENTS.md` phase list includes Phase 32 status and scope.
2. `notes/README.md` feature index aligns with final v3 doc set.
3. All new cross-links for v3 docs resolve correctly.

**Estimated Effort**: S (0.25 day)

### T09: One-Time Historical Backfill - Shadow Mode Delta Storage

**Description**: Run a one-time historical backfill action for pre-existing closures to populate `shadow_mode_deltas` for comparison reporting; runtime writes remain in T01.

**Acceptance Criteria**:

1. Historical backfill uses the `shadow_mode_deltas` table contract created in `P32-E01-T14`; runtime closure writes are handled by T01.
2. Stored records include deal linkage, entity type, `persona: v.optional(incentivePersonaValidator)`, `config_version_id: v.optional(v.id("incentive_config_versions"))`, v2 result JSON, v3 result JSON, delta summary, and timestamp.
3. `by_entity_type` index key order is `["entity_type", "persona", "created_at"]`.
4. Backfill process materializes missing historical rows deterministically and idempotently.
5. Delta persistence supports both per-closure drill-down and aggregate reporting windows.

**Estimated Effort**: S (0.25 day)

### T10: Safety - Anti-Double-Pay Enforcement

**Description**: Enforce uniqueness guardrails before creating new incentive disbursement rows.

**Acceptance Criteria**:

1. Disbursement creation checks for an existing payout for the same `closure_id` + `recipient_user_id`.
2. Duplicate-pay attempts are blocked with a clear, auditable error path.
3. Check is race-safe under retry/concurrent execution scenarios.

**Estimated Effort**: S (0.25 day)

### T11: Property Tests - Shadow Rollout and Migration

**Description**: Add property tests validating rollout parity, migration toggles, and anti-double-pay behavior.

**Acceptance Criteria**:

1. Tests validate paise-level rounding correctness for v2/v3 delta calculations.
2. Retry/idempotency tests ensure no duplicate disbursement side effects.
3. Edge cases include zero profit, single contributor, and all modifiers disabled.

**Estimated Effort**: M (0.5 day)

### T12: Analytics - `getShadowModeDelta`

**Description**: Add dedicated analytics query contract for shadow mode parity analysis.

**Acceptance Criteria**:

1. `getShadowModeDelta` query is implemented in `convex/analytics.ts`.
2. Query reads from `shadow_mode_deltas` and supports time-window/persona/entity filters.
3. Response includes per-deal rows plus aggregate variance metrics for admin dashboards.

**Estimated Effort**: S (0.25 day)
